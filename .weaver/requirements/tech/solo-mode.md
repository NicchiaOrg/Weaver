# Solo mode

## solo-mode

- **Where:** one module of `weaver-core` reads the state, finds the exclusions file and the prefix, writes and removes the block and lists the tracked files (`requirements/rules#solo-mode`). The CLI and the Tauri backend both call it; the UI never runs git.
- **git:** started with `crates/core/src/process.rs` `command` (no shell, no console window on Windows), cwd the project root, `GIT_OPTIONAL_LOCKS=0`, looked up on the PATH. Every call has a 10 s limit and is killed after it, through a time-limited runner shared with omp's (today `omp::run::run_command`, moved out of the omp module). A start failing with not-found means `git was not found`; `rev-parse` exiting 128 means `this folder is not in a git repository`. No git call runs on the UI or IPC thread (`requirements/quality#General`).
- **Calls:** `git rev-parse --show-prefix --git-path info/exclude` once per operation; tracked files with `git ls-files -z --cached --ignored --exclude=<line>` for each line of the block, run in the repository's root; nothing else.
- **Initialisation:** after the existence and agent-file conflict checks, and before any agent file or `.weaver/` is written, the block is written; `solo/solo.json` is written with `.weaver/`. When a later step fails, the rollback removes the block too. With `solo: off`, git is not called.
- **Changes in the app:** a Tauri command `set_solo_mode {projectId, mode}` runs in the project's mutation queue under the project lock, like the other project writes, and returns the new state or the error. The CLI's `project edit {solo}` goes to the running app the same way, or runs itself under the project lock.
- **State in the app:** `ProjectStatus` carries `solo`: `mode`, `unavailable` (the reason Solo mode cannot be changed, absent when it can) and `problem` (why the block could not be put in place at the last opening, absent otherwise), sent with `project-state`. The tracked files come from a command `solo_tracked_files {projectId}`, which the Settings view calls each time it is shown, and from the result of every change; they are never computed while Settings is not shown.
- **Opening:** when a project window opens on an initialised project, with an empty Model or a Model, a repair runs in the project's background work, coalesced like the opening check of the installed files and in the same run when both are due. Its outcome only sets or clears `solo.problem`; it never changes the opening check's outcome, its toast or its banner. It writes only when the block is missing or different.
- **`.weaver` vanishes:** on `PROJECT_FOLDER_REMOVED`, before anything else, the block of this working copy is removed, found by its markers alone; a failure is logged and nothing is shown.
- **Command line:** `solo` in `project new` and `project edit` input, values `off`, `folders`, `files`; output `solo` as `{mode, unavailable?, problem?, tracked}`, `tracked` being the list of tracked files, empty when Solo mode is off. `project show` and `project edit {solo}` compute it at the call: `problem` says why, while Solo mode is on, the block is not in place as expected; the command line never repairs it.
- **File view listing:** `git check-ignore -v -z --stdin` reports, for each ignored path, the file, line and pattern that decided it. A path decided by a line inside a Solo mode block of the exclusions file (of any working copy) is listed; the exclusions file is read once per listing to find those lines.
- **Installed texts:** the generated command reference mentions `solo`; the check of words that installed texts must not contain no longer lists `solo`.

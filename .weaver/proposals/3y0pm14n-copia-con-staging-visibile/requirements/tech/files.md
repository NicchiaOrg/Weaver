# Files

## files
- **Where:** listing, reading, writing, creating, renaming, moving, copying in and deleting files of the code live in `weaver-core` (sync `std` I/O); `src-tauri` exposes them as Tauri commands run in `spawn_blocking`. The UI never touches a file and still gets no `fs` plugin.
- **Paths:** commands take paths relative to the project root, with `/` separators. The backend refuses absolute paths, `..` parts, any path inside `.git`, and any path whose canonical form (`dunce`, case-insensitive on Windows) leaves the canonical project root. A symbolic link whose target leaves the root is listed, but cannot be opened, written, renamed into or moved into. The only absolute paths are the sources of a drop from outside, as Tauri reports them; their canonical form must lie outside the canonical project root.
- **State:** per project window, in backend memory only: the File view's state, its expanded folders and their entries, its tabs (path, hash read, line ending, byte order mark, why it is read-only) and the agent locks. Nothing of it is written to disk, enters the project picture or reaches `project-changed`. The UI renders what the backend sends and holds only the editors' texts and their undo history.
- **Events:** the backend sends the UI an event when a listed folder changes, when a tab's file changes, disappears or reappears on disk, and when a lock is taken or released; each carries the window's project id and a generation number.

## file-view
- **Listing:** one folder at a time with `read_dir`: names and kinds (file, folder, symbolic link) only, never a file's content, never recursion, never a search or an index. `.git` is left out by name. What git ignores is left out with one `git check-ignore -z --stdin` per listed folder, with `GIT_OPTIONAL_LOCKS=0`, as `crates/core/src/project_files/folder_tree.rs` does; without git, or outside a repository, nothing is ignored. Other names starting with a dot are listed. Folders first, then files, each sorted by name, case-insensitively.
- **Watching:** a `notify` watcher per project window for the File view, separate from the project watcher: one non-recursive watch per expanded folder, the root included, and one per file open in a tab. Collapsing a folder drops its watch and those of every expanded folder inside it. Events are batched per folder, 150 ms after the last one, and a batch reads that folder again. Temp files of atomic writes are ignored. None of these events reaches the project picture, its batcher or `workspace.FILES_CHANGED`. On Linux, an `ENOSPC` from inotify switches these watches to the poll watcher, as for the project.
- **Release:** when the view stops being shown its tabs are dropped at once; the folder watches and listings are dropped when the release delay passes, measured by an injected clock, unless the view is shown again first. Closing the window drops everything at once.
- **Create:** an empty file with `create_new`, or a folder with `create_dir`; never replaces an existing entry.
- **Rename and move:** one `rename` on the same volume that never replaces an existing entry (checked first, and with `renameat2(RENAME_NOREPLACE)` on Linux, `renamex_np(RENAME_EXCL)` on macOS and `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows). A move across volumes is refused with the reason. Tabs on the entry, or on files inside it, take the new path.
- **Delete:** with the `trash` crate, to the system's trash; when the trash refuses or is unavailable, the deletion is refused with its reason and nothing is deleted. Tabs on the entry, or on files inside it, close.
- **Dragging rows:** the tree uses pointer events, never the HTML5 drag and drop API (no `draggable`, no `dragstart`/`dragover`/`drop` handlers): `pointerdown` with the primary button on a row, `setPointerCapture`, the drag starting past the 4 px threshold, the target found with `document.elementFromPoint` on each `pointermove`, the move through the existing `files_move` command on `pointerup`, cancelled by `Esc`, `pointercancel` or a lost capture. The drag label is a fixed-position element with `pointer-events: none`. A press that never passes the threshold reaches the row's click as before.
- **Drops from outside:** Tauri's native drag-drop handler stays on for every window (never `disable_drag_drop_handler()`, never `dragDropEnabled: false`), because it is what reports dropped files with their paths, here and in the request editor. The File view listens with `getCurrentWebview().onDragDropEvent` only while it is shown: `enter` and `over` give the pointer in physical pixels, divided by `devicePixelRatio` and hit-tested with `document.elementFromPoint` against the tree; `drop` inside the tree sends the paths and the target folder to the copy command; `leave`, or a drop outside the tree, clears the highlight. The request editor keeps its own listener, which acts only while it is shown.
- **Copy in:** one Tauri command per drop runs the copy in `spawn_blocking`; a window holds at most one running copy, and the command refuses a second with the reason. Every refusal of `requirements/rules#file-view` is checked for every dropped entry before anything is written. Entries are read with `symlink_metadata`, never following a link: a file is created with `create_new` and its bytes copied, keeping its permission bits; a folder with `create_dir`, then its entries one by one, depth first; a symbolic link is recreated with the same target (`std::os::unix::fs::symlink`; on Windows `symlink_file` or `symlink_dir`, whose refusal, for example for lack of privilege, fails the copy). Nothing is ever replaced. The command records each top-level entry it created; when any step fails it removes those entries for good (not to the trash, since they are the drop's own copies) and returns the failing name and reason. The copy runs to its end even when the view stops being shown or the window closes; its result then goes nowhere, and the window's single-copy guard goes with the window. The folder watches report the new entries as for any outside change.
- **Copy in staging:** the copy is made in a staging folder `.copy-in.<random>.tmp` created inside the target folder, and each top-level entry is then moved to its place with a `rename` that never replaces an existing entry. The staging folder is a temp name the File view's watches ignore, but a listing shows it, like any other name starting with a dot, while the copy runs. When a step fails, the staging folder and the entries already moved are removed for good; when that removal fails too, what is left stays in the project and the error toast lists those entries with the reason instead of saying `Nothing was copied.`.
- **Refusals** come from `requirements/rules#file-view`, checked again in the backend when the command runs; a refused command changes nothing.

## file-tab
- **Opening:** a file is read only when it opens in a tab, and again only after an event of its own watch or a reload asked by the developer. The raw bytes are read once; binary and size come from `requirements/rules#file-tab`. The tab keeps the SHA-256 of the raw bytes, whether they start with a UTF-8 byte order mark, and the line ending chosen for saving. The UI gets the text without the byte order mark and with LF line endings.
- **Colours:** `@codemirror/language-data` picks the language by file name, then by extension; each language is loaded with a dynamic import the first time a file of its kind opens. Files over the size limit get no language. No WASM: the CSP stays as it is.
- **Saving:** the command carries the tab's text and the hash it read. Under a per-file lock in the backend, Weaver reads the file again and compares the SHA-256 of its raw bytes with that hash: when they differ, or the file is gone, nothing is written and the UI is told which. Otherwise the text is written with the tab's line ending, the byte order mark when there was one, and no other change, through the atomic write of `crates/core/src/atomic.rs` (temp `.<name>.<random>.tmp` in the same folder, `sync_all`, rename, Windows retries), giving the temp file the permission bits of the file it replaces. When the path is a symbolic link, the write goes to its target inside the project. `Overwrite` and `Keep mine` skip the comparison; `Save again` writes only when no file exists at the path.
- **Self-writes:** after a save the tab keeps the hash it wrote; a watch event whose file has that hash is not `workspace.OPEN_FILE_CHANGED`.
- **Moved by the agent:** when a released lock says where the agent moved the file, the tab takes that path and reads it there; its watch moves with it.

## file-lock
- **Source:** the live ACP `session/update` notifications of every job, of General and of every Ask more conversation of the project; never the updates replayed while a session loads. Sub-agents' transcripts and the `task` tool never count.
- **Tools that count:** `tool_call` and `tool_call_update` whose `kind` is `edit`, `delete` or `move`. omp reports its edits, writes and the deletions and moves inside an edit as `edit`; `execute`, `other` and the rest never count.
- **Start:** a tool counts from its `tool_call`. With `locations` it counts for those paths; with none it counts for every file open in a tab, until it ends. `locations` arriving in later updates of a running tool add their paths.
- **End:** a `tool_call_update` with status `completed` or `failed` ends the tool. Every tool of a conversation also ends when its turn ends or fails, when its omp exits or its connection closes, when its job ends (Done, Failed, Stopped), when General is cleared, and when an Ask more conversation closes.
- **Moves:** on a completed edit, the final `locations` hold the destination; when the result's `rawOutput.details` names as source a file open in a tab (`sourcePath`), the released lock carries the destination. These fields are omp internals: check them again at every rise of `MIN_OMP_VERSION`, as the sub-agent fields of `requirements/tech#job`.
- **Paths:** `locations[].path` are absolute. They are compared with the open files in canonical form; a path that no longer exists is compared as its parent's canonical form plus its name. Paths outside the canonical project root, git worktrees included, are ignored.
- **Memory:** the running tools of each conversation are kept in backend memory even while the File view is closed, with no disk work, so that a file opening during a tool opens locked.

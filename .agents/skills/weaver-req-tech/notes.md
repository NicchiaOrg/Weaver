# Notes

## notes-view

- **Where:** reading and writing the sheet, copying images in, naming them, reading them for display and moving them to the trash live in `weaver-core` (sync `std` I/O, pure functions where possible); `src-tauri` exposes them as Tauri commands run in `spawn_blocking`. The UI never touches a file and still gets no `fs` plugin.
- **Files:** the sheet is `.weaver/notes/notes.md`; images are `.weaver/notes/<name>` beside it (`requirements/rules#notes-view`). Commands take image names, never paths; the backend builds the path after checking the name and refuses any name with a separator, starting with `.`, or equal to `notes.md`. The folder is created, with its `.gitignore`, by the first write of the sheet or of an image, as every local-only folder (`requirements/data#General`).
- **Reading:** one command returns the sheet's text, or none when the file is missing, with the SHA-256 of its bytes. A CRLF file is read as LF.
- **Writing:** one command takes the whole text and writes it atomically with the shared writer (`requirements/data#General`), UTF-8 with LF, and returns the new hash. The UI writes 500 ms after the last change, at once after a tick, and when the editor loses the focus, the view is left or the window closes; before a window closes or the app quits, the backend asks that window's UI for the sheet's waiting text as `requests-flush` does for the request editor, with the same time limit, and writes it. At most one write per window runs at a time; texts that arrive meanwhile coalesce into one more write of the latest. Typing never waits for a write.
- **Editor:** TipTap 3 in React (`@tiptap/react`): `@tiptap/starter-kit` with its `Underline` left out and `Link` set to open nothing on click (`openOnClick: false`, `autolink: true`, `linkOnPaste: true`, protocols `http` and `https`), `TaskList` and `TaskItem` from `@tiptap/extension-list` with `nested: true`, `@tiptap/extension-image` as a block, `@tiptap/extension-placeholder`, and `@tiptap/markdown`, which reads the file with `contentType: 'markdown'` and writes it with `editor.getMarkdown()`. These modules load with one dynamic `import()` the first time the Notes view opens in a window, as `mermaid` does; the rest of the UI never imports them.
- **Unsupported content:** every block token of the file that no extension maps (raw HTML, tables, footnotes, front matter, conflict markers…) becomes one `rawMarkdown` block node that holds its source text as plain, editable text and writes it back byte for byte. Unknown inline syntax stays as text.
- **Ticks:** a checkbox click or `Cmd/Ctrl+Enter` is one ProseMirror transaction that only changes that `taskItem`'s `checked` attribute, so the written file differs only by that item's marker.
- **Images:** an image node keeps its Markdown destination as written. Only a destination that is exactly the name of a file in `.weaver/notes/` is shown: the UI asks the backend once per name for `data:<mime>;base64,<…>`, from one read, the MIME type from the signature as in `requirements/tech#file-tab` (Images), and keeps it in memory until a `notes-changed` names that image or the view's state is dropped. Any other destination (another path, `http`, `https`, `data:`) is never read nor fetched and shows the placeholder. The `<img>`'s `error` event also shows the placeholder.
- **Paste and drop:** images pasted come from `ClipboardEvent.clipboardData.files`; the UI sends each one's bytes and file name, when it has one, to one copy command. Files dropped from outside come from `getCurrentWebview().onDragDropEvent`, listened to only while the Notes view is shown, as the Assets view does (`requirements/tech#asset-view`); the UI sends their absolute paths and the drop position. The backend reads sources with `symlink_metadata`, never following a link, checks the kind by extension and signature and the size, picks the name, and creates each file with `create_new`, never replacing anything. It returns, per file, the name given or the reason it was refused or left out; the UI then inserts the added images at the cursor or at the drop position, in the order given.
- **Watching:** no new watcher. The project watcher (`requirements/tech#project`) already sees `.weaver/notes/`; its events there go only to the Notes view, batched 150 ms after the last one, and never reach the project picture, its rebuild, `project-changed` or `workspace.FILES_CHANGED`. Each batch is sent to the project's window as a `notes-changed` event with the project id, a generation number, whether the sheet changed (with its new hash, none when missing) and the names of the images that changed. A change of the sheet whose hash equals the last one Weaver wrote or read is not sent. It is `workspace.NOTES_CHANGED`.
- **Outside change:** on a `notes-changed` for the sheet, with no write waiting, the UI reads the sheet and replaces the editor's content in one transaction marked as not the developer's, so it is not counted in the removed images; with a write waiting, it writes at once and shows the toast of `requirements/ui#notes-view`.
- **Removed images:** the UI keeps, for the visit, the names of the images that leave the document through the developer's own transactions, undo and redo included. On `developer.LEAVE_NOTES_VIEW` and before the window closes, after the waiting text is written, it sends those that the written Markdown no longer names to one command that moves each to the system's trash with the `trash` crate, one at a time; the result lists the names the trash refused, with their reasons. The set then starts empty.
- **State:** per project window, in UI memory only: the editor with its undo history, cursor and scroll, the hash of the text shown, the removed images and the image cache. When the view opens again and the sheet's hash is the one shown, the editor is kept as it was; otherwise its content is replaced from disk. Nothing of it is written to disk besides the sheet and its images.
